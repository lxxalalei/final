# 学习资源需求澄清系统讨论交接

## 交接目的

供后续 ChatGPT 会话继续讨论 `resource-intent` 的产品定义与语义模型。本阶段只讨论需求澄清，不讨论现有六阶段流水线的搜索、平台执行、筛选、下载和归档实现。

## 已确认的产品边界

系统最终是一个面向家长和孩子的学习资源收集助手。

需求澄清的目标是：理解孩子的学习场景，并把用户表达转化为清晰、可靠、可执行的资源收集需求。

建议使用下面这句话约束后续设计：

> 在不过度追问的前提下，把孩子的学习场景翻译成资源收集任务：为怎样的孩子，围绕什么内容，收集能帮助他完成什么学习任务的资源，这些资源将怎样使用，并需要满足哪些条件。

## 明确排除的方向

- 不扩展成泛儿童成长咨询系统。
- 不覆盖一般性的亲子关系、情绪心理、健康或家庭教育咨询，除非它们直接构成具体学习资源需求的必要背景。
- 不引入教师作为目标用户。当前用户是家长和孩子。
- 不把需求澄清等同于搜索关键词生成。
- 不在 Intent 中决定平台、搜索词、查询数量、下载或归档策略。
- 不强迫用户解释深层原因；理解到足以收集合适资源即可。
- 不把资源形式偏好当成完整学习需求。

## 需求澄清的六个维度

这六项是需求维度，不是固定的六个执行阶段。运行时不能依次盘问；只澄清会显著影响资源收集的未知项。

1. **学习内容**：孩子具体要学习什么。
2. **学习任务**：启蒙、理解、预习、同步学习、练习、复习、测评或拓展。
3. **资源作用**：资源需要讲解概念、示范方法、提供练习、检查掌握程度、激发兴趣或支持家长陪学。
4. **学习者条件**：年龄、年级、当前基础等真正影响资源适配的信息。
5. **使用方式**：孩子自主使用、家长陪伴、打印练习、路上听或其他明确场景。
6. **资源要求**：必须满足、优先满足和明确排除的形式、语言、版本、费用、时长等条件。

前三项构成核心需求，后三项用于适配和筛选。

## 总体澄清原则

### 区分模糊、宽泛、未指定和歧义

- **模糊**：无法判断应收集什么，例如“找点学习资源”。
- **宽泛**：用户明确要求广泛覆盖，例如“先看看有哪些英语启蒙资源”。这是合法需求。
- **未指定**：用户没有表达某项偏好，可以保持开放。
- **歧义**：当前表达可能导向明显不同的资源内容，且用户并未要求广泛探索。

只有模糊和会改变资源路线的关键歧义需要澄清。

### 澄清影响测试

提问前检查：如果不问，是否很可能收集到另一类资源？

- 会改变内容范围、难度或资源作用：考虑澄清。
- 只影响候选排序，或者可以通过广泛收集覆盖：不澄清。

### 不做机械槽位收集

- 一次只问一个高价值问题。
- 用户已经说清楚时停止提问。
- 未知信息可以省略。
- 明确事实、用户判断、系统推断必须分开。
- 不能把系统推测伪装成用户事实。

## 已讨论维度一：学习内容

### 定义

学习内容回答：

> 这批资源在内容上应该帮助孩子学习什么？

它不负责表达学习目的、使用方式或资源形式。

### 内容层级

不应继续使用一个 `core_topic` 混合所有语义。学习内容至少存在以下层级：

```text
学习领域 → 主题 → 具体学习点 → 内容范围
```

示例：

```text
数学 → 应用题 → 两步应用题的数量关系 → 四年级上册范围
英语 → 阅读 → 根据上下文猜词 → 小学高年级短文
科学 → 天文 → 太阳系行星 → 入门科普范围
```

不要求每次四层齐全。用户明确到哪一层，就保留到哪一层。

### 内容类型

建议开放识别以下类型，不建立封闭分类：

- 学科知识：数学、语文、英语、科学。
- 具体知识点：分数、自然拼读、光合作用。
- 学习技能：审题、概括主旨、口语表达。
- 学习方法：做笔记、检查作业、背单词。
- 兴趣主题：恐龙、太空、汽车、历史。
- 实践技能：绘画、实验、手工、编程。

### 问题描述不等于学习内容

“孩子做应用题不知道从哪里下手”应区分：

- 用户观察：不知道从哪里下手。
- 已明确学习内容：应用题。
- 候选学习点：审题、数量关系、解题步骤。

候选学习点不能未经澄清就作为确认事实。可以询问：“他主要是读不懂题意，还是理解题意后不知道先算什么？”

### 宽泛内容可以直接成立

- “找四年级数学系统课程”：用户主动要求系统覆盖，无需追问具体知识点。
- “找英语启蒙资源，先广泛看看”：不应强迫选择自然拼读或绘本。
- “孩子数学不好，找点资料”：无法判断计算、应用题还是概念理解，需要澄清。

### 上位概念不自动触发澄清

“编程”等词是否需要澄清取决于收集任务，而不是关键词本身：

- “先看看儿童编程有哪些学习资源”：可以广泛收集。
- “找一套可以马上开始学的编程课程”：Scratch、Python、机器人等路线会显著改变内容，应澄清。

### 多内容关系

需要保留并列、主次和独立关系：

- 并列相关：“古诗学习和朗诵”。
- 主次：“数学为主，补一点计算练习”。
- 独立：“三年级数学练习和儿童画教程”。

完全独立不代表必须让用户二选一。系统能够拆分收集任务时，应保留多个内容项。

### 学习内容的完成标准

- 能判断哪些资源相关、哪些明显无关。
- 内容粒度忠于用户要求，没有擅自缩小。
- 用户问题描述与系统解释分开。
- 多个内容之间的关系得到保留。
- 不存在会让资源走向完全不同领域的关键歧义。

## 尚未确认的问题

“专注力、时间管理、作业习惯”是否属于学习内容。

当前建议：只要明确发生在孩子学习场景中，就纳入“学习方法与学习习惯”；泛化的行为管理、情绪或亲子关系不纳入。

此边界需要下一轮由用户确认，确认后再写入正式领域词汇表。

## 建议的后续讨论顺序

1. 先确认学习内容是否包含学习习惯与学习方法。
2. 完成“学习内容”的澄清规则与测试场景。
3. 讨论第二维度“学习任务”，重点区分启蒙、理解、练习、复习、测评和拓展。
4. 继续讨论“资源作用”，避免将资源形式误当资源作用。
5. 最后再设计结构化 Schema 和可执行测试，不要先围绕现有字段修补。

## 现有实现中的重要问题

- 当前 `resource-intent` 更像搜索关键词预处理器，尚未完整表达学习场景与资源作用。
- `core_topic` 混合领域、主题、学习点和问题。
- 现有 `golden-cases.json` 没有真正执行 Intent 或比对语义期望；相关测试只检查案例数量与 ID 唯一性。
- `tests/e2e_pipeline_test.py` 的 Intent 输出是手写 fixture，只能验证数据契约，不能证明需求理解能力。
- 当前规则把“想学编程”机械判定为必须澄清，未区分用户主动要求广泛探索的情况。

## 建议调用的 skills

- `domain-modeling`：继续统一术语、讨论边界和维护领域词汇表。
- `grilling`：六个维度形成初稿后，用边界案例压力测试澄清规则。
