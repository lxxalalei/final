## 助手

先给结论：当前 `resource-intent` 更像“搜索关键词预处理器”，还不是“学习资源需求理解器”。

主要问题有四层：

1. Intent 的职责缺了一半  
   目前默认所有请求都是“搜索新资源”，但真正的助手还要区分：

   - 搜索/推荐新资源
   - 比较已有候选
   - 下载指定链接
   - 查询本地资源库
   - 补充、替换已有资源

   这些操作现在由 Flow 用自然语言自行判断，没有结构化 Intent 承接。

2. 学习需求模型太扁平  
   `core_topic` 混合了学科、知识点、问题和资源名称。例如：

   - “孩子应用题不会审题”
   - “找四年级数学课程”
   - “给家长找辅导孩子计算粗心的方法”

   现有模型都只能压成 `core_topic + learning_goal`，无法明确表达：

   - 谁学习、谁使用资源
   - 当前遇到什么问题
   - 希望产生什么学习结果
   - 资源承担什么作用：讲解、练习、测评、参考还是陪伴指导
   - 孩子直接使用，还是家长/教师先使用

3. 部分推断不可靠  
   当前示例把“四年级数学课程”推断为“系统学习”，还把“课程”直接当成资源形态。这未必成立：“课程”可能只是用户对内容集合的泛称，也可能是在找某个知识点的讲解。

4. 测试实际上没有测语义能力  
   [golden-cases.json](/Users/arale/Documents/learning_v0.1/resource-intent/examples/golden-cases.json) 中的 23 个案例没有真正运行 Intent。测试只检查案例数量和 ID 是否重复。  
   [e2e_pipeline_test.py](/Users/arale/Documents/learning_v0.1/tests/e2e_pipeline_test.py) 的 Intent 输出也是手写 fixture。因此现有测试通过，只能说明契约和校验器没坏。

我建议 Intent v2 分成两层：

```text
请求意图
├── 用户要执行什么动作
│   ├── discover / compare / download / library_lookup / update
│
└── 用户需要什么学习支持
    ├── 学习对象：谁要学
    ├── 资源使用者：孩子 / 家长 / 教师
    ├── 当前状态：不会什么、已有基础
    ├── 目标结果：理解、练习、复习、提升、解决问题
    ├── 内容对象：学科、主题、知识点
    ├── 资源作用：讲解、示范、练习、测评、参考、活动
    ├── 使用场景：自主学习、陪学、备课、路上听
    └── 硬约束、软偏好和排除条件
```

第一步我们需要先定 Intent 的能力边界。我的建议是：

> Intent 同时识别“用户要系统做什么”和“需要怎样的学习资源”；平台选择、关键词生成、搜索数量仍留给 Search。

同时，`search_concepts` 建议从 Intent 移到 Search。Intent 应输出稳定的需求语义，不应提前生成同义词和召回词。

## 用户

我们先不看整套流程，你先记住我们现在只做一个学习需求澄清系统，什么是学习需求澄清，这个系统该怎么做

---

## 助手

先把定义钉死：

> 学习需求澄清，是把用户模糊、表层或混杂的表达，转化为对“谁需要发生什么学习变化、目前卡在哪里、做到什么算解决”的清晰描述。

它不是搜索需求澄清，也不是资源偏好收集。

## 一、什么叫“学习需求”

学习需求不是“想要什么资源”。

“找四年级数学课程”是资源请求，不是完整的学习需求。它背后可能是：

- 想同步预习新课
- 某个知识点没听懂
- 基础薄弱，需要系统补齐
- 家长想了解四年级学什么
- 单纯想浏览课程

真正的学习需求应描述“现状与目标之间的差距”：

```text
当前状态 → 希望达到的状态
```

例如：

> 孩子四年级，做两步应用题时不会分析数量关系，希望能独立列式并说明解题思路。

这里才包含了一个相对完整的学习需求。

## 二、需要澄清哪些内容

核心不是填满槽位，而是形成五个关键认识：

1. 学习者  
   谁遇到了学习问题。当前范围内是孩子，表达者可以是孩子或家长。

2. 学习对象  
   要学习的知识、技能、方法或习惯。例如分数概念、英语听力、阅读概括、检查习惯。

3. 当前状态  
   现在会什么、不会什么、具体表现是什么。  
   “数学不好”不是状态；“应用题读完不知道先算什么”才是可用状态。

4. 目标状态  
   希望发生什么变化。  
   例如“能独立完成两步应用题”，而不是笼统的“提高数学”。

5. 适用边界  
   哪些条件会改变学习目标，例如年级、教材进度、已有基础、考试期限。只收集真正相关的条件。

“喜欢视频还是 PDF”“去哪个平台找”“要不要下载”都不属于学习需求澄清。

## 三、系统应该怎么工作

### 1. 先理解用户已经表达了什么

把信息分成：

- 明确事实
- 用户观察到的现象
- 用户自己的判断
- 系统推断
- 仍然未知的信息

例如“孩子粗心”只是家长判断。系统不能直接把它当成原因，应继续寻找可观察表现：

> 是看错题目、计算过程出错，还是做完后不会检查？

### 2. 识别真正影响理解的缺口

系统不应该看到缺字段就提问。它只判断：

> 当前信息能否说明孩子要解决什么学习问题？

如果不能，找出影响最大的未知点。

### 3. 一次提出一个有区分度的问题

问题应该区分不同学习方向，而不是让用户填写档案。

“孩子数学不好”时：

- 不应先问：“几年级？喜欢视频还是练习册？”
- 应先问：“目前最明显的是计算容易出错、应用题不会分析，还是课堂概念没理解？”

用户回答后，再判断年级是否真的必要。

### 4. 根据回答更新理解

系统需要区分：

- 新回答补充了信息
- 新回答修正了原判断
- 前后信息发生冲突
- 用户无法进一步描述

不能只做一次性槽位抽取。

### 5. 达到停止条件后输出学习需求描述

满足以下条件即可停止：

- 学习对象基本明确
- 当前问题或学习起点基本明确
- 希望达到的结果基本明确
- 没有会导致完全不同学习方向的关键歧义

输出应类似：

> 四年级孩子在两步应用题中难以识别数量关系，目前目标是学会拆解条件、确定先后步骤并独立列式。尚未确认具体教材版本，但不影响理解当前学习需求。

## 四、系统不应该做什么

- 不把资源名称当成学习目标。
- 不根据“粗心、坐不住”进行心理或医学诊断。
- 不为了完整而询问年龄、性别、平台、格式等信息。
- 不替用户编造深层原因。
- 不一轮提出五六个问题。
- 不强迫所有需求都追溯到“根本原因”。
- 用户已经说清楚时，不继续盘问。

## 五、建议的核心模型

```text
学习需求
├── learner：学习者
├── learning_object：要学习什么
├── current_state：当前表现或起点
├── target_state：希望达到的结果
├── context：会影响目标的必要背景
├── evidence：每项判断来自哪句话
└── unresolved：仍存在但不妨碍继续的未知项
```

最关键的验收标准不是“字段抽取得全不全”，而是：

> 澄清结果是否准确描述了孩子需要发生的学习变化，并且没有把系统推测伪装成用户事实。

下一步应该讨论“什么情况下算需求已经清楚，什么情况下必须继续问”。这是整个系统最核心的判断标准。

## 助手

对，刚才我把范围收窄成了“孩子要学什么”，这个定义不够。

更准确的定位应该是：

> 面向家长和孩子、以孩子成长为默认语境的用户需求澄清系统。

它要澄清的不只是学习问题，而是：

> 用户现在为什么来、涉及谁、发生了什么、希望系统做什么、最终想促成什么变化。

## 一、需求由两部分组成

### 1. 用户希望系统做什么

这是任务意图，例如：

- 帮我理解一个现象
- 给出解决建议
- 制定计划
- 推荐资源或活动
- 帮助家长和孩子沟通
- 比较几个选择
- 生成练习、故事或工具
- 陪孩子完成某件事
- 判断是否需要寻求专业帮助

### 2. 用户想解决什么成长问题

这是成长意图，例如：

- 学科学习
- 认知与能力发展
- 兴趣探索
- 学习习惯和自我管理
- 情绪与心理状态
- 社交与表达
- 亲子关系
- 行为与规则
- 身体发展和健康
- 安全与边界意识
- 品格与价值观

这两个维度必须分开。

例如“孩子不愿意写作业，给我推荐点资源”：

- 表面任务：推荐资源
- 成长问题：作业拖延
- 真实期望可能是：减少冲突、建立自主完成作业的习惯

如果只识别“推荐资源”，系统还是会跑偏。

## 二、必须分清不同角色

系统不能只有一个模糊的“用户”。

至少要区分：

- 请求者：当前是谁在说话，家长还是孩子
- 关注对象：当前主要在讨论谁
- 行动者：接下来需要谁采取行动
- 受益者：希望谁发生变化

例如：

> “我不知道怎么跟孩子谈成绩下降。”

这里：

- 请求者：家长
- 关注对象：孩子及亲子互动
- 行动者：家长
- 受益者：孩子和亲子关系
- 用户要系统做的事：提供沟通指导

再例如：

> “妈妈总逼我写作业，我不想回家。”

这里孩子既是请求者，也是首先需要被理解和保护的人。系统不能套用“帮助家长管理孩子”的视角。

## 三、需求澄清需要考虑的核心维度

不是每次全部询问，但系统应具备这些观察维度：

1. 谁在表达，涉及谁。
2. 用户明确要求系统做什么。
3. 是什么事情触发了当前请求。
4. 用户观察到了什么具体表现。
5. 用户如何理解这件事。
6. 用户最希望改变什么。
7. 谁能够或需要采取行动。
8. 场景发生在家庭、学校、同伴交往还是线上环境。
9. 年龄、发展阶段、持续时间、频率等是否会改变判断。
10. 是否有时间、经济、设备、家庭协作等现实限制。
11. 是否涉及安全、健康、心理危机或其他高风险情况。
12. 当前信息是否足够支持下一步服务。

其中要严格区分：

- 观察：“每天写作业要拖到十点。”
- 判断：“孩子就是不自律。”
- 推断：“可能缺乏时间管理能力。”

系统可以记录前两者，但不能把第三种直接当成事实。

## 四、“默认围绕孩子成长”的正确含义

它是解释语境，不是强行推断。

例如用户说“怎么改善沟通”，系统可以优先理解为家庭或亲子沟通，并在必要时确认。

但它不能：

- 把所有问题都归因于孩子。
- 默认改变对象一定是孩子。
- 把家长的焦虑自动解释成孩子的问题。
- 忽略孩子作为直接用户的感受和诉求。
- 把明确的其他需求硬套进成长框架。

很多场景真正需要改变的可能是家庭互动方式，而不是孩子本身。

## 五、系统的工作方式

```text
用户表达
→ 识别请求者和显性要求
→ 形成对成长场景的初步理解
→ 区分事实、判断、推断和未知
→ 检查风险
→ 找出最影响后续处理的歧义
→ 必要时只问一个高价值问题
→ 输出已澄清的用户需求
```

停止条件不是“所有维度都填满”，而是：

- 已经知道用户希望系统做什么；
- 已经知道主要涉及什么成长场景；
- 已经知道用户希望改变什么；
- 没有会导致错误处理或安全风险的关键歧义。

## 六、建议的概念名称

“学习需求澄清”已经太窄。我建议暂时称为：

> 儿童成长场景下的用户需求澄清

它的核心输出可以概括为一句话：

> 谁因为发生了什么，在什么背景下，希望系统提供什么帮助，以促成什么变化。

下一步应该先确定这个“一句话需求描述”需要包含哪些必需信息，再考虑分类、字段和澄清规则。

## 助手

对，合理边界应当是：

> 面向家长和孩子，理解孩子的学习场景，并形成可执行的学习资源收集需求。

需求澄清既不能只做关键词抽取，也不需要扩展到泛成长咨询。

## 需求澄清要解决什么

最终应回答六件事：

1. 为谁收集  
   孩子的年龄、年级、基础等，仅保留会影响资源适配的信息。

2. 围绕什么学习内容  
   学科、主题、知识点、能力或具体困难。

3. 想完成什么学习任务  
   启蒙、理解、预习、同步学习、练习、复习、测评、拓展等。

4. 资源要发挥什么作用  
   讲解概念、示范方法、提供练习、检查掌握程度、激发兴趣，或者支持家长陪学。

5. 如何使用  
   孩子自主使用、家长陪伴、打印练习、路上听、集中学习等。

6. 有哪些资源要求  
   必须满足、优先满足和明确排除的条件，包括形式、语言、版本、费用、时长等。

可以概括为：

```text
为怎样的孩子，
围绕什么内容，
收集能帮助他完成什么学习任务的资源，
这些资源将怎样使用，
并需要满足哪些条件。
```

## 学习场景与资源需求要分开

例如：

> 孩子四年级，应用题不知道从哪里下手，想找些带讲解和练习的资料。

学习场景：

- 四年级
- 应用题
- 不会分析解题步骤
- 目标是掌握解题思路

资源收集需求：

- 需要方法讲解
- 需要例题示范
- 需要配套练习
- 最好能从讲解过渡到独立完成

这两部分都需要，但 Intent 不负责判断去哪搜、使用什么搜索词。

## 不要过度追问“深层原因”

资源收集助手只需要理解到足以收集合适资源。

例如“找四年级数学系统课程”已经是合法且足够明确的需求。用户没有义务进一步解释成绩、薄弱点或家庭背景。

只有当歧义会导致收集完全不同的资源时才问：

- “孩子数学不好，找点资料”  
  需要问主要困难是计算、应用题还是概念理解。

- “找四年级数学系统课程”  
  不需要问为什么学，也不需要问喜欢什么媒介。

- “找恐龙科普资源，先看看有哪些”  
  这是明确的开放式收集，不应逼用户选择视频或图文。

所以必须区分：

- 模糊：不知道该收集什么。
- 宽泛：用户明确允许广泛收集。
- 未指定：用户没有偏好，可以保持开放。
- 歧义：存在两条明显不同的资源路线。

只有“模糊”和关键“歧义”需要澄清。

## Intent 的合理输出

最终不应只是一些槽位，而应形成一份“资源收集需求说明”：

> 为小学四年级孩子收集应用题学习资源，目标是帮助孩子理解数量关系和解题步骤。资源需要同时包含方法讲解、例题示范和专项练习，主要供孩子学习和练习使用。教材版本与文件格式未限定。

因此，Intent 的核心不是“猜用户真正的人生目标”，而是：

> 在不过度追问的前提下，把孩子的学习场景翻译成清晰、可靠、可执行的资源收集任务。

## 助手

要逐一讨论，但先纠正术语：这六个是“需求维度”，不是固定执行阶段。

系统运行时不能机械地按六步盘问用户，而应根据已有信息，只澄清会影响资源收集的维度。

建议按这个顺序讨论设计：

1. 学习内容：到底学什么。
2. 学习任务：启蒙、理解、练习、复习还是拓展。
3. 资源作用：资源具体要帮助完成什么。
4. 学习者条件：哪些年龄、年级、基础信息确实相关。
5. 使用方式：孩子自主、家长陪伴或特定场景。
6. 资源要求：必须、偏好、排除条件。

前三项构成核心需求；后三项负责适配和筛选。

每个维度都要讨论：

- 它解决什么问题
- 包含哪些概念
- 什么可以推断
- 什么不能推断
- 何时必须澄清
- 何时可以保持未知
- 如何测试是否理解正确

建议从第一个“学习内容”开始。这里首先要解决：主题、学科、知识点、能力和问题描述之间是什么关系。

## 第一维度：学习内容

“学习内容”回答的是：

> 这批资源在内容上应该帮助孩子学习什么？

它不回答学习目的、使用方式或资源形式。

### 1. 不能再用一个 `core_topic` 全部承载

学习内容至少存在不同层级：

```text
学习领域 → 主题 → 具体学习点 → 内容范围
```

例如：

```text
数学 → 应用题 → 两步应用题的数量关系 → 四年级上册范围
英语 → 阅读 → 根据上下文猜词 → 小学高年级短文
科学 → 天文 → 太阳系行星 → 入门科普范围
```

不要求每次四层齐全。用户明确到哪一层，就保留到哪一层。

### 2. 学习内容可以有不同类型

建议至少识别以下几类，但不要做封闭分类：

- 学科知识：数学、语文、英语、科学。
- 具体知识点：分数、自然拼读、光合作用。
- 学习技能：审题、概括主旨、口语表达。
- 学习方法：做笔记、检查作业、背单词。
- 兴趣主题：恐龙、太空、汽车、历史。
- 实践技能：绘画、实验、手工、编程。

分类的作用是帮助理解，不是要求用户先选分类。

### 3. 问题描述不等于学习内容

例如：

> 孩子做应用题不知道从哪里下手。

需要拆成：

- 用户观察：不知道从哪里下手。
- 学习内容：应用题。
- 可能的学习点：审题、数量关系、解题步骤。

其中“应用题”有直接证据；“审题、数量关系”只是候选解释，不能直接当成已确认事实。

合适的澄清问题是：

> 他主要是读不懂题意，还是理解题意后不知道先算什么？

回答后才能进一步确定学习内容。

### 4. 宽泛内容也是合法需求

不能把“宽泛”自动判定成“模糊”。

- “找四年级数学系统课程”  
  内容范围明确且用户主动要求系统覆盖，不需要追问具体知识点。

- “找英语启蒙资源，先广泛看看”  
  用户明确要求广泛探索，不应强迫选择自然拼读或绘本。

- “孩子数学不好，找点资料”  
  不知道资源应该围绕计算、应用题还是概念理解，需要澄清。

关键判断是：

> 用户是否明确选择了广泛收集，还是系统无法判断该收集哪类内容？

### 5. “编程”等上位概念不应自动触发澄清

现有规则认为“想学编程”必须在 Scratch、Python、机器人之间选择，这过于机械。

应该结合用户任务：

- “先看看儿童编程有哪些学习资源”  
  可以广泛收集，不澄清。

- “给孩子找一套可以马上开始学的编程课程”  
  不同路线会导致完全不同内容，应澄清。

是否澄清不仅由内容词决定，还取决于用户是否需要定向收集。

### 6. 多个学习内容要保留关系

需要区分：

- 并列相关：“古诗学习和朗诵”。
- 主次关系：“数学为主，补一点计算练习”。
- 完全独立：“三年级数学练习和儿童画教程”。

完全独立不代表一定要让用户二选一。系统能支持多任务收集时，可以拆成两个内容项；只有执行范围受限时才询问先做哪个。

### 7. 这一维度的完成标准

学习内容已经清楚，应满足：

- 能判断哪些资源相关、哪些明显无关。
- 内容粒度符合用户原本要求，没有擅自缩小。
- 问题描述与系统解释明确分开。
- 相关的多个内容没有被强行合并。
- 不存在会让资源走向完全不同领域的关键歧义。

现在有一个需要确定的边界：

> “专注力、时间管理、作业习惯”是否算本系统的学习内容？

我的建议是：只要明确发生在孩子学习场景中，就纳入“学习方法与学习习惯”；泛化的行为管理、情绪或亲子关系则不纳入。

## 助手

整体项目结构冲击不大，但 `Intent → Search` 的数据契约需要明显调整。

原因是当前下游对 Intent 的程序耦合很弱，大部分依赖存在于 Skill 指令和 Schema，不在平台执行代码中。

| 模块 | 冲击 | 原因 |
|---|---:|---|
| `resource-intent` | 高 | 语义模型、Schema、规则、验证器、案例都要重做 |
| `resource-search` | 中 | 要适配新的学习内容、学习任务和资源作用；接管 `search_concepts` |
| `resource-selector` | 中低 | 脚本只校验 session，主要修改语义审查规则 |
| `learning-resource-flow` | 低 | 仍只关心 `ready / needs_clarification` 和问题 |
| 平台搜索适配器 | 很低 | 消费的是 Search Plan，不直接读取 Intent |
| Downloader | 无或很低 | 基本不受 Intent 结构影响 |
| Library Manager | 低 | 后续需要调整主题和学习任务的归档映射 |
| 测试 | 高 | 当前语义测试基本无效，需要建立真正的案例执行与对比 |

六阶段主结构可以保留：

```text
Intent → Search → Platforms → Selector → Downloader → Library
```

需要改变的是 Stage 1 的内部模型：

```text
当前：
slots
├── core_topic
├── learning_goal
├── resource_types
└── search_concepts

建议：
learning_content
learning_task
resource_roles
learner_context
usage_context
requirements
```

最大的接口变化是两点：

1. `core_topic` 不再是唯一必填核心。
2. `search_concepts` 从 Intent 移到 Search，由 Search 根据澄清后的需求生成召回概念。

建议不要直接修改 `intent-spec/v1`，而是建立 `intent-spec/v2`，然后一次性更新 Search 的输入契约。这样已有会话和测试 fixture 不会被悄悄解释成新语义。

所以结论是：

> 不需要推翻项目架构；需要重构 Stage 1，并同步调整 Stage 2 和语义测试。代码执行层受影响很小，主要工作量在领域模型、规则和测试案例。

现在重新讨论正是成本最低的时候。等平台、筛选和资料库大量依赖旧 Intent 字段后再改，冲击才会真正变大。

## 助手

需要像 Intent 一样重新讨论的，主要是 Search 和 Selector。其余阶段更偏工程能力审查。

| 阶段 | 是否需要重新定义 | 重点 |
|---|---:|---|
| 1. Intent | 必须深入讨论 | 什么才是可执行的资源收集需求 |
| 2. Search | 必须深入讨论 | 如何把学习需求转成互补的资源收集方案 |
| 3. Platforms | 需要能力审查 | 每个平台能搜什么、结果是否真实完整、失败如何处理 |
| 4. Selector | 必须深入讨论 | 什么资源算相关、有用、适龄，以及如何组成候选集合 |
| 5. Downloader | 主要做工程审查 | 下载能力、授权边界、格式、降级和失败恢复 |
| 6. Library | 需要讨论，但可后置 | 怎么分类、复用、检索，以及保存哪些需求语义 |
| Flow | 最后整体讨论 | 澄清、搜索、选择、下载之间如何与用户交互 |

## 三个必须深入讨论的核心阶段

### Intent：理解要收集什么

输出清晰的资源收集需求。

### Search：决定应该寻找哪些资源

Search 不能只是把主题拼成关键词。需要回答：

- 当前学习任务需要哪些互补的资源作用？
- 是只找一套系统课程，还是组合讲解、示例和练习？
- 哪些内容路径值得覆盖？
- 用户要求广泛探索时，覆盖到什么程度？
- 不同平台各自承担什么职责？

Intent 说明“需要什么”，Search 负责“为了满足它，应该去寻找什么”。

### Selector：判断找到的资源是否真的有用

Selector 不能只做标题相关性和热度排序，需要讨论：

- 内容是否真的支持当前学习任务？
- 适龄、难度、版本是否匹配？
- 资源承担什么作用？
- 一批候选如何形成互补组合？
- 系统应该替用户过滤到什么程度？
- 哪些未知信息必须提示用户？
- 质量、相关性和展示顺序如何区分？

这三个阶段构成核心语义链：

```text
Intent：用户需要什么
   ↓
Search：应该寻找什么组合
   ↓
Selector：哪些结果真正满足需求
```

## Platforms 不需要做同类型的领域讨论

Platform 应尽量保持“执行器”定位：

- 接收查询
- 调用真实搜索能力
- 返回规范化结果
- 如实报告失败

它不应该理解孩子的学习需求，也不应该做最终质量判断。

但需要逐个平台进行能力审计，尤其检查：

- 搜索接口是不是真实有效
- 查询有没有被平台正确使用
- 返回结果是否丢失关键字段
- 是否存在伪搜索、固定结果或错误降级
- 平台能力描述是否与实际代码一致

## Downloader 和 Library

Downloader 主要是工程可靠性问题，不需要像 Intent 一样重新建模。

Library 则取决于产品定位。如果资料库只是保存文件，影响较小；如果希望以后支持“找到之前为孩子收集的同类资源”，就需要保存学习内容、学习任务和资源作用，届时要单独讨论资料库语义模型。

## 推荐讨论顺序

1. Intent：六个需求维度。
2. Search：资源作用与收集覆盖策略。
3. Selector：相关性、质量和候选组合。
4. Platform：逐个平台做真实能力审计。
5. Downloader：下载和降级可靠性。
6. Library：归档与复用模型。
7. Flow：最后统一交互和阶段衔接。

前三个决定这个系统是否“懂学习资源”，后三个决定它能否稳定地把事情做完。
