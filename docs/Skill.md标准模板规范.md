# Skill.md 标准模板规范（穿插式执行版）

> **版本**：v1.0
> **核心思想**：SKILL.md 就是可执行的剧本——模型照着文档从上往下读，就知道每一步该做什么。

---

## 一、设计原则

### 1.1 核心思想

**"执行即阅读"**——模型读 SKILL.md 的过程，就是执行任务的过程。

不要把"输入格式"、"输出格式"、"执行步骤"分成三个独立章节。
而是把数据字段的说明，穿插在**用到它的那一步**旁边。

### 1.2 对比

**旧写法（分离式）**：
```
## 输入格式
（一大段 JSON 格式说明）

## 输出格式
（一大段 JSON 格式说明）

## 执行步骤
第一步：...
第二步：...
```

**新写法（穿插式）**：
```
## 执行步骤

### 第一步：读取上游输入
从 {session_dir}/stage1_intent.json 读取 data 部分
需要用到的字段：
- core_topic：核心主题，用于...
- queries：查询列表，用于...

### 第二步：处理逻辑
...

### 第三步：写入输出文件
写入 {session_dir}/stage2_search.json
需要写入的字段：
- total_count：候选总数
- resources：候选资源列表，每个包含...
```

## 二、标准结构

每个 Skill 的 SKILL.md 按以下顺序组织：

```
1. 头部信息（frontmatter）
   - name
   - description

2. 一句话定位
   - 我是谁
   - 上游是谁（从哪接收数据）
   - 下游是谁（把数据传给谁）

3. 执行前准备
   - 从哪个文件读输入
   - 需要哪些参数
   - 工作目录在哪

4. 执行步骤（核心部分，从上往下读就能执行）
   每一步都包含：
   - 做什么（动作）
   - 用什么数据（从哪来、字段说明）
   - 产生什么结果（写到哪、字段说明）

5. 完成后动作
   - 写入哪个输出文件
   - 怎么通知 flow
   - 返回什么摘要信息

6. 参考资料（可选，放附录位置）
   - 详细规则文档
   - 质量标准
   - 其他参考
```

---

## 三、关键约定

### 3.1 路径占位符

统一使用以下占位符，模型执行时替换为实际值：

| 占位符 | 含义 | 示例 |
|--------|------|------|
| `{session_dir}` | 会话目录（绝对路径） | `/path/to/sessions/20260626-1441-math` |
| `{input_file}` | 上游输入文件名 | `stage1_intent.json` |
| `{output_file}` | 本阶段输出文件名 | `stage2_search.json` |
| `{workspace}` | 工作区根目录 | `/path/to/.learning-resource-work` |

### 3.2 三层文件结构

所有阶段文件统一三层结构，这个是全系统约定，每个 Skill 都要遵守：

```json
{
  "_meta": { ... },      // 元数据（阶段、时间、来源等）
  "_summary": { ... },   // 摘要（flow 读这个做调度）
  "data": { ... }        // 完整业务数据（下游 Skill 读这个）
}
```

每个 Skill 只需要关注 **data 部分**的字段，_meta 和 _summary 是固定格式。

### 3.3 读写规则

- **读**：只读取上游阶段文件的 `data` 部分，不修改上游文件
- **写**：只写自己的阶段文件，完整覆盖写入
- **不碰**：不修改其他阶段的文件，不修改 manifest.json（flow 负责）

## 四、字段说明的写法

在用到某个字段的地方，用以下格式说明：

### 4.1 输入字段说明

```markdown
**需要读取的字段**：
- `field_name`：字段含义说明
  - 类型：string / number / array / object
  - 可选/必选：✅ 必选 / ⚠️ 可选
  - 示例："示例值"
```

### 4.2 输出字段说明

```markdown
**需要写入的字段**：
- `field_name`：字段含义说明
  - 类型：string / number / array / object
  - 要求：必须包含 / 建议包含
  - 示例："示例值"
```

### 4.3 简写形式

如果字段简单，可以用更紧凑的写法：

```markdown
读取 `data.core_topic`（核心主题字符串）作为搜索关键词
```

---

## 五、执行步骤的标准写法

每个执行步骤建议包含：

1. **步骤标题**：清晰说明这一步做什么
2. **动作描述**：1-2 句话说清楚做什么
3. **数据输入**：从哪读、读什么字段
4. **处理逻辑**：怎么处理
5. **数据输出**：产生什么结果、存到哪（如果这一步有中间输出）

---

## 六、完整模板

```markdown
---
name: skill-name
description: 一句话描述这个 Skill 是做什么的
---

# Skill 名称 · 一句话定位

## 我是谁

**上游**：xxx-skill（从哪里接收数据）
**下游**：xxx-skill（把数据传递给谁）
**阶段编号**：stage N

一句话说明这个 Skill 的核心职责。

---

## 执行前准备

### 1. 确认输入文件

从 flow 传入的参数中获取：
- `{session_dir}`：会话目录路径
- `{input_file}`：上游输入文件名（通常是 stage{N-1}_xxx.json）
- `{output_file}`：本阶段输出文件名（通常是 stage{N}_xxx.json）

### 2. 读取输入

读取 `{session_dir}/{input_file}` 文件，提取其中的 `data` 部分。

> 💡 只需要读 `data`，`_meta` 和 `_summary` 可以忽略（flow 用的）

---

## 执行步骤

### 第一步：[步骤名称]

[1-2 句话说明这一步做什么]

**需要读取的字段**（从 data 中）：
- `field1`：字段说明
  - 类型：string
  - 必选：✅
- `field2`：字段说明
  - 类型：array
  - 必选：⚠️ 可选

**处理逻辑**：
1. ...
2. ...
3. ...

**本步产出**：（如果有中间结果）
- 临时变量 xxx，用于下一步

---

### 第二步：[步骤名称]

...

---

### 第三步：写入输出文件

处理完成后，将结果写入 `{session_dir}/{output_file}`。

**文件格式**（三层结构）：

```json
{
  "_meta": {
    "stage": N,
    "session_id": "从输入文件或参数中获取",
    "skill": "skill-name",
    "created_at": "当前时间（ISO 8601）",
    "input_from": "{input_file}"
  },
  "_summary": {
    // 给 flow 看的摘要，≤10 个字段
  },
  "data": {
    // 给下游 Skill 用的完整业务数据
  }
}
```

**_summary 需要写入的字段**（flow 读这个做调度决策）：
- `field1`：摘要字段 1
- `field2`：摘要字段 2

> 💡 _summary 必须精简，flow 只读前几十行就知道结果怎么样。

**data 需要写入的字段**（下游 Skill 读这个）：
- `field1`：字段说明
  - 类型：string
  - 必选：✅
- `field2`：字段说明
  - 类型：array
  - 必选：✅

---

## 完成后

1. 确认输出文件已写入 `{session_dir}/{output_file}`
2. 向 flow 返回执行结果，格式如下：
   ```
   ✅ 已完成 [阶段名称]
   📄 输出文件：{output_file}
   📊 摘要：
   - 字段1：值1
   - 字段2：值2
   ```
3. 只返回 _summary 的内容，不要在上下文中展开完整 data

---

## 参考资料

- **[文档名称]**：`./references/xxx.md`（详细说明）
- **[规范名称]**：`./references/schemas/xxx.md`（权威标准）

> 💡 参考资料放在最后，执行时不需要看，需要时再查阅。
```

## 七、改造检查清单

改造一个 Skill 后，用这个清单检查：

- [ ] 模型只需要从上往下读，就能完整执行任务
- [ ] 每一步都明确知道读什么文件、写什么文件
- [ ] 数据字段的说明就在用到它的步骤旁边
- [ ] 输入输出文件路径用占位符表示
- [ ] 明确区分 _summary（给flow）和 data（给下游）
- [ ] 完成后动作清晰（写什么、返回什么）
- [ ] 参考资料放在最后，不干扰主流程阅读
