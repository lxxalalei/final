# resource-search

## 任务边界

读取 `{session_dir}/stage1_intent.json`，仅在 `data.status=ready` 时生成
`{session_dir}/stage2_search_plan.json`。

完整理解 `clarified_need`，用 `evidence` 区分用户事实与模型推断，用
`requirements` 继承 `must`、`prefer`、`exclude` 的原有强度。不要重新澄清需求。

本 Skill 生成一次性的多平台搜索计划，只决定：

- 当前需求值得从哪些互补方向搜集；
- 每个方向由哪个可执行平台承担最合适；
- 向每个平台发送哪些原生查询及多少结果预算。

不执行搜索、筛选结果或下载资源，也不查看结果、不判断单条资源质量。不要规划学习方法、学习习惯或教师备课资源；产品范围是孩子学习场景中的资源收集，家长可以是选择者或陪伴使用者。

输入输出遵循 `../docs/pipeline-data-contract.md`。输出版本为 `search-plan/v1`，可执行平台及参数以 `config/platform-catalog.json` 为准。

## 决策流程

### 1. 建立当前需求的覆盖地图

读取 `references/coverage-strategy.md`。先在内部形成当前需求专属的覆盖地图，至少考虑：

- 内容切面：哪些知识、文本、现象、步骤或子主题共同构成这次搜集；
- 资源作用：说明、原始材料、示范、练习、实验、朗读、拓展等哪些作用真正有用；
- 使用与媒介：孩子如何使用，视觉、听觉、阅读、打印或动手是否带来不可替代的价值；
- 来源类型：哪些方向需要权威或结构化来源，哪些适合创作者讲解或公共文化内容；
- 检索表达：正式名称、教材表达、儿童常用说法、现象词或具体任务词中哪些能打开不同结果集合。

这些是模型的思考坐标，不是固定分类，也不是输出字段。只保留对当前需求有实际贡献的方向，不为“全面”平均凑齐媒介或资源类型。

### 2. 让平台为每个方向竞争

读取 `references/routing-rules.md`。对每个候选方向比较：

1. 平台内容与该方向是否天然匹配；
2. 能否比 generic 或其他平台更稳定地提供独特资源；
3. 平台查询是否能用其原生生态表达，而非统一关键词换平台；
4. 当前适配器的认证要求与运行可靠性是否值得投入预算；
5. 是否符合用户的必需、偏好和排除条件。

将方向交给预期边际收益最高的平台。多个平台结果高度重叠时保留更合适者；一个平台可承担多个相近方向，但查询必须各有职责。

每份计划必须恰好有一个 `generic/P0`，用于跨站发现、权威来源和未接入站点的公开页面。它是必要基线，但不要求排在数组第一，也不阻塞其他任务。对当前需求具有核心且独特价值的专业平台也可以是 `P0`，与 generic 同波并行。

完成语义选择后再读取 `config/platform-catalog.json`：

- 只有 `planning_status=available` 的平台能成为独立任务；
- planned 或未注册来源只能通过 generic 发现公开页面；
- `params` 只使用 catalog 声明且本次真实需要的参数；
- 认证信息由 Platform 管理，不写入计划。

### 3. 生成平台原生查询组合

读取 `references/query-strategy.md`。每条查询应打开一个有意义的结果集合：改变内容切面、资源作用、来源类型或使用方式，而不是只替换同义词或添加统一后缀。

通常一次搜集安排 6—12 条互补查询；用户明确要求尽量全面时可增至 12—20 条。这只是预算参考，不是配额：窄需求可以更少，低贡献平台应直接省略。

- generic 通常 2—4 条，负责不同来源或资源作用；
- 核心专业平台通常 1—3 条；
- 补充或探索平台通常 1—2 条；
- 每条通常取 8—15 个结果，窄方向可少，稀缺方向可适当加深。

不要在站内平台查询中使用 `site:`、`filetype:`，也不要加入“高赞”“播放量高”等接口不能保证的质量词。质量与适龄性最终由 Selector 结合真实结果判断。

### 4. 分配优先级

- `P0`：若缺失会明显破坏主要覆盖的基线或核心来源；generic 固定为 P0。
- `P1`：贡献明确、能够补充主要覆盖的来源。
- `P2`：较窄、探索性强，或运行可靠性较低的来源。

优先级表示执行波次，不表示资源质量。同一优先级的平台可以并行。不要因平台已接入就自动加入，也不要用 P2 保存没有明确价值的任务。

## 输出

```json
{
  "_meta": {
    "schema_version": "search-plan/v1",
    "session_id": "继承上游",
    "created_at": "ISO 8601"
  },
  "data": {
    "search_tasks": [
      {
        "platform": "generic",
        "priority": "P0",
        "searches": [
          {
            "query": "围绕当前需求的可执行查询",
            "max_results": 12,
            "params": {"engines": ["baidu", "bing"]}
          }
        ]
      }
    ]
  }
}
```

每个平台只创建一个任务。输出只保留执行层会消费的字段；不要添加覆盖地图、平台理由、质量预测、思考过程或汇总计数。平台分工应能从查询组合中看出。
每个 `searches[]` 元素对应一次真实平台调用，包含查询、结果上限及该平台支持的可选参数。

## 完成前自检

1. 每条查询是否能说清它会带来哪一类不同结果？删除任一条会损失什么？
2. 内容、作用、媒介和来源覆盖是否来自当前需求，而不是固定模板？
3. 每个专业平台是否利用了该平台的真实内容优势和查询方式？
4. 是否存在两个平台承担相同职责，却没有足够的独特增益？
5. 是否恰好包含一个 `generic/P0`，并让重要专业平台获得了与贡献相称的优先级？
6. 运行不稳定或需认证的平台是否只有在独特价值足够高时才加入，并适当降低优先级？
7. 所有限定词是否来自用户证据，或确实用于改善当前方向的召回？
8. `requirements` 的强度是否被完整保留，且没有加入学习方法、习惯或教师资源？
9. 所有平台和 `params` 是否由 catalog 支持？

运行：

```bash
python3 resource-search/scripts/validate_output.py \
  {session_dir}/stage2_search_plan.json \
  --intent {session_dir}/stage1_intent.json
```

结构验证不能代替上述语义自检。完成后向 Flow 返回输出路径。
